# 04 仿真先行

> **规则：任何算法或控制逻辑的改动，先在主机上跑通，再进固件。**
>
> 板上一次迭代：编译 1~3 min + 烧录 30 s + 观察/复位 1~5 min ≈ 5 分钟起。
> 主机上一次迭代：编译 2 s + 运行 0.1 s ≈ 3 秒。
> **差 100 倍**，且主机可重复、可覆盖边界。

---

## 1. 三级仿真

按"离硬件的远近"分三级，成本递增、保真度递增。

| 级别 | 环境 | 能验证什么 | 不能验证什么 |
|---|---|---|---|
| **L1 离线算法** | Python/WSL/Octave | 数学正确性、边界、收敛性、参数敏感性 | 时序、定点误差、硬件非理想 |
| **L2 主机固件** | PC + fake HAL | 真实 C 代码、状态机、浮点误差、接口契约 | 中断竞争、GPIO 时序、模拟电路 |
| **L3 硬件在环** | 真板 + 脚本 | 一切真实行为 | 大范围参数扫描（太慢） |

**原则**：能 L1 解决的别用 L2，能 L2 解决的别用 L3。

### 1.1 三套环境各自的职责（别混用）

| 环境 | 典型工具 | 用来做 | 别用来做 |
|---|---|---|---|
| **WSL / Linux** | Python + numpy/scipy、Octave | 算法原型、控制器设计、参数扫描、画 Bode/阶跃 | 编译固件（路径风格与工具链不匹配） |
| **Windows + 工具链自带 shell** | msys2 / git-bash + mingw gcc | 编译固件逻辑（`test/host`），跑断言 | 大范围数值实验（迭代慢、画图不便） |
| **板子 + 串口脚本** | Python + pyserial | 真机验收、保护验证、精度标定 | 参数扫描（每次都要烧录/等待） |

> ⚠️ 本工程踩过的坑：主机测试脚本 `build.sh` 里写的是 `/d/...` 路径和
> Vitis_HLS 的 msys2 gcc，**只能用 msys2 的 bash 运行**。
> 用 WSL 的 `bash` 跑会落到 `/usr/bin/gcc`，报 `undefined reference to 'cosf'`，
> 把真正的错误掩盖掉（详见 3.6）。

## 2. L1：离线算法仿真（WSL / Python）

### 2.1 适用场景

- 控制器结构选型（PID / 类型 II / 带前馈）
- 滤波器设计与相位补偿
- 观测器/状态机的数学正确性
- 参数敏感性分析（扫参数看鲁棒性）
- 饱和、积分饱和、抗饱和策略

### 2.2 做法

```python
# sim_ctrl.py —— 与固件同构的离散仿真
import numpy as np

Ts = 50e-6          # 与固件 Ts 一致
N  = int(0.5 / Ts)

def plant(w, v, i):        # 简化的电机模型
    ...

for k in range(N):
    i_ref = ctrl(w_err)    # 与固件完全相同的控制律
    ...
```

**关键要求**：
1. **Ts 必须与固件一致**（离散化的差异是 bug 的常见来源）
2. **饱和/限幅必须建模**（真实系统 90% 的问题出在饱和）
3. **量纲显式**（每行注释单位，避免 Hz/rad·s⁻¹ 混淆）

### 2.3 输出什么

- 波形图（响应曲线、误差曲线）
- **量化指标**：超调、建立时间、稳态误差、相位裕度
- 参数扫描表（哪个参数最敏感 → 决定了实机调试的重点）

### 2.4 与固件的"同构"原则

仿真代码与固件代码**应当结构一致**（同样的控制器结构、同样的限幅位置），
只允许在"被控对象模型"上不同。

否则会出现：仿真通过、实机不通过，且无法判断是模型问题还是代码问题。

## 3. L2：主机固件测试（fake HAL）

### 3.1 核心思想

把**算法层**编译到 PC 上运行，用"假硬件"替换 HAL：

```
User/Alg/*.c   （算法，不含任何 HAL 调用）
User/Mid/*.c   （中间层，HAL 调用被 fake 替换）
test/host/fake/
    hal_stub.c       ← 空实现的 HAL 函数
    bsp_xxx_fake.c   ← 可控的假外设
    fake_api.h       ← 测试注入接口
```

### 3.2 目录结构

```
test/host/
├── build.sh            # gcc 编译 + 运行
├── test_main.c         # 测试用例（断言计数）
└── fake/
    ├── hal_stub.c      # HAL_GetTick / HAL_Delay … 空或可控
    ├── bsp_flash_fake.c# 假 Flash（内存数组，可注入损坏数据）
    ├── bsp_ssi_fake.c  # 假编码器帧（可注入 CRC 错、越界）
    └── *_fake.h
```

### 3.3 设计要点

| 要点 | 说明 |
|---|---|
| **算法层零 HAL 依赖** | 否则无法在主机编译 |
| **假外设可编程** | 能注入正常/异常/边界数据 |
| **测试用断言计数** | 输出 `checks: N failed: M`，便于 CI 判定 |
| **可跑"黄金值"** | 用实机测得的典型值做回归基准（防止改坏） |

### 3.4 典型用例

```c
/* 1. 边界 */
CHECK(ctrl_step(0.0f) == 0.0f);
CHECK(ctrl_step(1e9f) <= LIMIT_MAX);          /* 饱和 */
CHECK(!isnan(ctrl_step(NAN)));                 /* 输入异常 */

/* 2. 状态机 */
reset();
CHECK(state() == IDLE);
event(START);
CHECK(state() == RUN);

/* 3. 黄金值（实机标定的参数） */
CHECK_NEAR(calc_k(2.3f, 0.5e-3f), 0.00311f, 1e-6f);
CHECK_NEAR(ff_acc(9e-5f, 4.13e-3f, 7), 3.11e-3f, 1e-7f);

/* 4. 异常注入 */
fake_flash_corrupt(0);                         /* 坏 CRC */
CHECK(load_param() != 0);                      /* 必须拒绝 */
```

### 3.5 收益（本工程实测）

- 发现"单位算错 7 倍"：`J/KE_elec` 误写成 `J/(KE·pp)`，主机断言立刻抓到
- 发现"编译期断言在 ARMCC5 不可用"：用负数组技巧替代，主机可验证
- 建立 538 条断言，之后每次改动 1 秒内回归

### 3.6 工具链环境陷阱（真实案例，务必设防）

**事故**：主机测试脚本 `build.sh` 的源文件列表里混进了一个多余的反斜杠
（`$ROOT\/User/Alg/alg_pll.c`），该行被 bash 当成字面路径，编译时报
`No such file or directory`；同时因为脚本是"用 `bash` 调用"的，
实际执行的却是 **WSL 的 bash + WSL 的 gcc**（脚本里的 `/d/...` 路径只在
msys2 下成立），于是错误信息变成了 `undefined reference to 'cosf'`
（缺 `-lm`），**真正的错误被掩盖**。

**三层教训**：

| 层 | 教训 |
|---|---|
| 脚本 | 路径拼接不要出现裸 `\`；源文件列表一行一个，缩进对齐，便于肉眼比对 |
| 环境 | 脚本必须在**它设计的那套 shell** 里运行（本工程是 Vitis_HLS 的 msys2 bash），不能想当然用 WSL 的 `bash` |
| 诊断 | 报错信息与"预期错误"不符时，先确认**你跑的是哪个编译器**（`command -v gcc`、`gcc --version`），再查代码 |

**加固措施（建议照做）**：

```bash
# 脚本开头打印环境，让"跑错环境"立刻暴露
echo "bash : $BASH_VERSION"
echo "gcc  : $(command -v gcc)"
"$(command -v gcc)" --version | head -1
```

```text
# 并把"正确调用方式"写进 test/README.md，例如
D:\Xilinx\Vitis_HLS\2022.2\tps\win64\msys64\usr\bin\bash.exe -lc \
  "cd /d/<项目路径> && bash test/host/build.sh"
```

**通用原则**：仿真脚本的首要敌人不是算法，而是**环境漂移**
（不同 shell、不同 gcc、不同路径风格）。把环境固定下来并让脚本自证环境，
比多写十条断言更有价值。

## 4. L3：硬件在环（串口脚本）

### 4.1 适用场景

- 真实时序、中断、外设配置
- 保护动作、异常场景
- 精度验收（必须用真实传感器）

### 4.2 做法

用 Python + pyserial 驱动交互命令，脚本化操作：

```python
def ask(s, cmd, t=0.2):
    s.reset_input_buffer()
    s.write((cmd + '\r\n').encode())
    time.sleep(t)
    return s.read(300000).decode('ascii', 'replace')

def fn(text, pattern, cast=float):
    m = re.search(pattern, text)
    return cast(m.group(1)) if m else None
```

**要点**：
1. **每条命令都要能解析出数值**（固件输出的格式要为此设计）
2. 脚本开始先 `stop` 复位（保证初始状态已知）
3. 等待用"轮询状态"而不是"固定 sleep"（更快也更稳）

### 4.3 固件要配合设计

为了让脚本能验证，固件必须提供：

| 能力 | 例子 |
|---|---|
| 状态查询命令 | `stat`、`fault`、`<模块>` |
| **结构化输出** | `ref 1400 rpm, meas 1401 rpm, iq 0.08 A` （便于正则） |
| 内部量可见 | 关键中间变量要能打印（`diag` 行） |
| 可复位 | `stop`、`clr` |

> **没有可观测性就没有验收**。
> 在方案阶段就要设计"怎么观测"，而不是事后加打印。

### 4.4 波形抓取（可选进阶）

若固件有波形输出（CSV/二进制），脚本可直接解析：

```python
def grab_csv(s, nch, secs=1.2):
    buf = read_for(s, secs)
    rows = []
    for ln in buf.decode('ascii','replace').split('\n'):
        if ln.count(',') == nch - 1:
            rows.append([float(x) for x in ln.split(',')])
    return rows
```

用途：验证通道映射、验证量纲、抓瞬态。

## 5. "仿真先行"的执行检查表

改动前自问：

- [ ] 这个改动有算法/逻辑成分吗？（有 → 必须 L1 或 L2）
- [ ] 变化量能被主机断言捕获吗？（能 → 加一条断言）
- [ ] 有没有边界（0、饱和、NaN、溢出）需要覆盖？
- [ ] 仿真的 Ts、量纲、限幅位置与固件一致吗？
- [ ] 如果仿真通过但实机失败，我如何区分"模型问题"与"代码问题"？

改动后：

- [ ] 主机测试全过
- [ ] 仿真结论（若有新洞察）写进 `00_开发日志`
- [ ] 新增的断言保留在 `test/host` 里（作为回归）

## 6. 不适用的场景（直接上板，但要写明理由）

| 场景 | 为什么不仿真 |
|---|---|
| GPIO 复用/时钟树配置 | 无法脱离芯片验证 |
| 外设时序（SPI 极性、ADC 触发链） | 依赖具体硬件 |
| 中断优先级与竞争 | 主机无法复现 |
| 模拟前端（运放、分流电阻） | 物理特性 |
| 上电/掉电时序 | 依赖电源设计 |

**要求**：在阶段方案里写明"此项不做仿真，依据：…"，并提高该项的实机验证强度。
