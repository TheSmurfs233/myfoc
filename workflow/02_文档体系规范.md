# 02 文档体系规范

> 文档不是"写给人看的报告"，而是**项目的可执行记忆**。
> 判断一份文档是否合格：**换一个人（或换一个 AI 会话）能否只靠它继续工作。**

---

## 1. 编号规则

采用"十进制分段 + 前缀"，一眼看出文档性质：

| 段 | 用途 | 示例 |
|---|---|---|
| `00~09` | **过程文档**（日志、进度、决策） | `00_开发日志`、`01_项目进度` |
| `10~29` | **框架文档**（架构与子系统） | `10_框架_主框架`、`13_框架_ADC采样` |
| `30~39` | **使用文档**（面向操作者） | `30_命令手册`、`31_参数表` |
| `40~59` | **方案与评估**（一次性深度文档） | `43_无感方案评估` |
| `90~99` | **遗留与已知问题** | `90_已知问题与限制` |

**规则**：
- 编号只增不改，废弃文档标注"已废弃"但**不删**（历史可追溯）
- 新增框架文档时，接在同类编号末尾，不要插队

## 2. 必备文档清单

### 2.1 四份"永远存在"的文档

| 文档 | 作用 | 更新频率 |
|---|---|---|
| `00_开发日志.md` | 时间线事实记录，含**每次实验的数据** | 每次实验 |
| `01_项目进度.md` | 唯一"现在做到哪"的事实来源 | 每阶段 |
| `10_框架_主框架.md` | 系统怎么跑起来的（分层、时序、数据流） | 架构变化时 |
| `90_已知问题与限制.md` | 已知缺陷、不打算修的问题、规避方法 | 每次发现 |

> **`01_项目进度` 是单一事实来源**。
> 任何"做完了吗"的问题，答案只能在它里面，不能散落在聊天记录里。

### 2.2 按需必备

| 触发条件 | 必须新建的文档 |
|---|---|
| 出现第一条交互命令（串口/按键/网络） | `30_命令手册.md` |
| 出现第一个可调参数 | `31_参数表.md` |
| 进入需要反复调试的阶段 | `32_调试指南.md` |
| 出现第一个"待确认"的技术问题 | `18_待确认清单.md` |
| 某个子系统超过 ~500 行 | 该子系统的 `1x_框架_xxx.md` |
| 做出重要技术选型 | 写入 `00` 的"决策记录" + 方案文档 |
| 交付给他人使用 | `37_使用指南.md`（分步骤、含期望输出） |

## 3. 每类文档的写法

### 3.1 开发日志（`00`）

**唯一规则：追加，不改旧条目。**

每条包含：

```markdown
## YYYY-MM-DD · <一句话主题>

### 背景 / 问题
<现象、触发条件、当时在做什么>

### 数据
| 项 | 值 |
|---|---|
<必须是实测值，不是估计>

### 分析
<推理链：从数据到结论>

### 结论与动作
<改了什么、为什么这样改>

### 验证
| 项 | 结果 |
|---|---|
```

**禁忌**：
- ❌ "优化了一下性能"（无法复现）
- ✅ "速度阶跃 rise 0.2 ms → 0.15 ms（`sstep 0.5` 实测），因为把 PI 的 ki 从 0.05 提到 0.08"

### 3.2 进度表（`01`）

**一行一个阶段**，列固定的五列：

```markdown
| 阶段 | 名称 | 状态 | 验收标准 | 证据/版本 |
|---|---|---|---|---|
| S4 | 开环起动 | ✅ 完成 | 起转成功率 ≥ 9/10 | 10/10，固件 #142 |
```

**状态取值只允许五种**：`⬜ 未开始`、`🟡 进行中`、`✅ 完成`、`⚠️ 完成但有保留`、`❌ 放弃（原因）`

**禁忌**：不要写"基本完成""差不多好了"。要么达标，要么没达标。

### 3.3 框架文档（`10`~`2x`）

固定七节结构（模板见 `templates/t_框架文档.md`）：

1. **职责**：这个模块负责什么、不负责什么
2. **接口**：对外函数/命令/参数
3. **数据结构**：关键结构体与状态机
4. **时序**：在哪个中断/任务里跑、频率、耗时
5. **算法/流程**：核心公式与流程（含单位、量纲）
6. **参数**：可调项、默认值、取值范围、影响
7. **坑与注意事项**：踩过的坑（这一节最有价值）

### 3.4 命令手册（`30`）

必须包含：
- 完整命令列表（**行数与代码中的 help 一致**，可用脚本校验）
- 每条命令的参数、取值范围、返回示例
- 错误码/错误信息对照表

### 3.5 参数表（`31`）

必须包含：宏/变量名、含义、**单位**、默认值、范围、影响面、修改是否需要重新标定。

> 单位必须写。同一个量在不同层用不同单位（如 Hz / rpm / rad/s）
> 是嵌入式项目最常见的 bug 来源。

### 3.6 已知问题（`90`）

| 编号 | 现象 | 影响 | 触发条件 | 规避方法 | 状态 |
|---|---|---|---|---|---|

**"不打算修"的问题也必须写进去**，并写明理由。

## 4. 写作硬规则

| 规则 | 说明 |
|---|---|
| **数字优先** | 每个结论附数值/日志片段；禁止"更快""更稳"这类形容词 |
| **单位必写** | `46.7 Hz` 而不是 `46.7`；注意 rpm/Hz/rad·s⁻¹ 的换算 |
| **公式带量纲** | `E = ω_e × ψf`，并注明 ψf 的单位 |
| **表格列数一致** | 用 `doc_check.py` 自动检查（否则渲染错乱） |
| **相对路径** | 文档之间用相对路径互链，避免工程搬家失效 |
| **ASCII 进代码，中文进文档** | 源码注释若要 ASCII-only（部分工具链限制），中文说明放文档 |
| **TBD 集中** | 所有未定项进 `18_待确认清单`，正文不留 `TBD`（用脚本扫描） |

## 5. 文档检查自动化（`doc_check.py`）

文档一旦超过 10 份，人工核对必然失守。用脚本守三条底线：

### 5.1 检查项

| 检查 | 目的 |
|---|---|
| 表格列数一致性 | 防止渲染错乱、防止"看起来有内容其实错位" |
| **版本号一致性** | `01_项目进度` 里写的固件版本 == 代码里的 `FW_BUILD_ID` |
| 帮助行数 / 通道数 / 枚举项数 | 代码与文档的计数必须相等 |
| TBD 残留扫描 | 正文里的未定项必须收敛到 `18_待确认清单` |
| 编码异常字符 | 防止 PowerShell/编辑器把中文写成 `\x0B` 之类的控制字符，或写出替换字符 U+FFFD |

### 5.2 版本号一致性的重要性

这是**投入产出比最高的一条**：

```
代码里的 FW_BUILD_ID = 163
文档里写 "固件 #160"        → 立刻报错
```

它保证了"文档描述的行为"与"板上跑的固件"是同一版本。
没有这条，你会花大量时间怀疑"是不是没烧进去"。

### 5.3 实现要点（伪代码）

```python
errors = []
# 1) 版本号
src_ver = re.search(r'FW_BUILD_ID\s+(\d+)u', read('User/Cfg/board_cfg.h')).group(1)
for doc in ('docs/01_项目进度.md', 'docs/README.md'):
    for m in re.finditer(r'#(\d+)', read(doc)):
        if m.group(1) != src_ver:
            errors.append(f'{doc}: 版本号 {m.group(1)} != 代码 {src_ver}')

# 2) 表格列数
for doc in glob('docs/*.md'):
    for i, line in enumerate(read(doc).split('\n')):
        if line.startswith('|') and line.endswith('|'):
            cells = count_unescaped_pipes(line) - 1
            ... 与表头比较 ...
# 3) 帮助行数
help_lines = count(re.findall(r'CODE_HELP', read('app_cmd.c')))
# 4) TBD 残留（跳过 00 与 18）
```

> 表格里的 `|` 必须写成 `\|`，否则列数统计会错——
> 这是最容易踩的坑，脚本要能报出具体行号。

## 6. 文档的"过期"治理

文档过期比没有文档更危险（会误导后来的推理）。治理方法：

| 手段 | 说明 |
|---|---|
| 版本号绑定 | 版本一变，所有写死旧版本号的地方立刻报错 |
| 每阶段结束 `grep` 一次 | 搜索旧参数值、旧阈值、旧命令名 |
| 决策记录保留 | 被推翻的结论**不删**，标注"已推翻，原因：…" |
| 引用而非复制 | 参数只在 `31_参数表` 写一次，其他地方用链接引用 |

---

## 7. 最少工作量的合规做法

时间紧张时，按此优先级保底：

1. `01_项目进度` 必须准确（否则不知道做到哪）
2. `00_开发日志` 每次实验一条（哪怕只写数据表）
3. `31_参数表` 与代码同步（否则调参靠猜）
4. `90_已知问题` 至少记录"会咬人的"几条
5. `doc_check.py` 只保版本号一致性这一条
