# 01 开发流程总纲

> 本文定义项目的**五个阶段**与**五个门禁**。
> 阶段是"能力的成长"，门禁是"过关的条件"。二者不可混用。

---

## 1. 五个阶段

| 阶段 | 名称 | 产出 | 典型时长 |
|---|---|---|---|
| **A** | 立项与需求 | 需求清单、约束、验收总目标 | 1~3 天 |
| **B** | 方案与架构 | 方案文档、框架文档骨架、阶段计划 | 3~7 天 |
| **C** | 分阶段实施 | 每阶段：方案 → 仿真 → 实现 → 验证 → 提交 | 主要工期 |
| **D** | 集成与整机验证 | 全链路联合测试、边界与异常测试 | 1~2 周 |
| **E** | 交付与文档冻结 | 使用手册、已知问题、参数表定稿 | 2~3 天 |

---

## 2. 五个门禁

每一个门禁都是**"没有证据就不放行"**。

### G1 需求门禁（A → B）

- [ ] 需求写成条目，每条**可验证**（有数值阈值或可观测现象）
- [ ] 硬件约束写清楚（引脚、供电、传感器量程）
- [ ] 明确"这一版不做什么"（防止范围膨胀）

### G2 方案门禁（B → C）

- [ ] 总体方案有**备选路线**，并写明为什么选当前这条
- [ ] 阶段划分完成（见 `03_阶段推进与验收`）
- [ ] 每阶段的验收标准已量化
- [ ] 风险清单与对策
- [ ] 评审记录归档（谁、何时、结论）

### G3 阶段门禁（C 内，每个阶段）

一个阶段只有同时满足下列条件才算完成：

- [ ] 验收标准**逐条**实测通过（数据进开发日志）
- [ ] 构建 0 错误 0 警告
- [ ] 主机测试全过
- [ ] 文档检查通过
- [ ] 相关框架文档已更新
- [ ] 已提交并推送

> **禁止跳阶段**。发现前一阶段有缺陷时，回到那个阶段补，
> 不要在新阶段里"顺手绕过去"——那会变成技术债。

### G4 集成门禁（D → E）

- [ ] 全链路（上电 → 初始化 → 运行 → 停止）反复通过
- [ ] 异常场景逐项验证（断电、传感器失效、过载、通信中断）
- [ ] 保护动作全部实测触发过，且*不会误触发*
- [ ] 长时运行（≥ 30 min）无漂移、无累积误差

### G5 交付门禁（E 结束）

- [ ] 使用手册能让人在不问你的情况下跑起来
- [ ] 参数表与实际代码逐项核对一致
- [ ] 已知问题清单完整（含"不打算修"的）
- [ ] 版本号、固件 ID、文档基线一致（可用脚本校验）

---

## 3. 阶段内的标准动作（最重要）

每个阶段内部按固定五步执行，**顺序不可颠倒**：

```
① 方案   写成文档 → 评审
② 仿真   主机/离线/仿真器验证算法与逻辑（见 04_仿真先行）
③ 实现   写固件，版本号 +1
④ 验证   三方验证（见 05_验证与提交规范）
⑤ 提交   一个阶段一个提交，信息含证据
```

### 为什么"仿真"必须排在"实现"前面

- 算法的错误在仿真里是**几十毫秒**的迭代成本，在板上是**几十分钟**（编译+烧录+观察）
- 仿真是**可重复**的，板上的现象受温度、摩擦、供电噪声影响，难以复现
- 仿真能覆盖**边界**（0、饱和、溢出），板上很难刻意制造

例外：纯硬件时序、外设配置、引脚复用这三类无法仿真，直接上板，
但必须写在方案里（"此项不做仿真，依据：…"）。

## 4. 文档与阶段的关系

| 文档 | 何时写 | 何时更新 |
|---|---|---|
| `00_开发日志` | 每天/每次实验 | **追加式**，永不改旧条目 |
| `01_项目进度` | 立项 | 每阶段结束 |
| `10_框架_主框架` | 方案阶段 | 架构变化时 |
| `11+_框架_子系统` | 该子系统进入实施前 | 该子系统每次改动 |
| `18_待确认清单` | 随时 | 有了结论就迁出 |
| `30_命令手册` | 出现第一条交互命令 | 每次增删命令 |
| `31_参数表` | 出现第一个可调参数 | 每次增删参数 |
| `90_已知问题` | 发现第一个已知限制 | 每次新增/关闭 |

> **判断标准**：如果"另一个你会问什么"，就把那个问题的答案写下来。

## 5. 阶段划分的原则

好的阶段划分满足：

1. **每个阶段产出一种可独立验证的能力**（不是"写了一堆代码"）
2. **后一阶段依赖前一阶段的输出**（否则可以并行或合并）
3. **每个阶段的失败是"局部"的**（不会让此前工作全部作废）
4. **每个阶段都能在 1~5 天内完成**（超过就再拆）

反例（错误划分）：
- ❌ "实现全部功能" —— 无法验证，无法定位失败
- ❌ "先写驱动，再想怎么测" —— 阶段没有验收标准

正例（本工程实际划分）：

```
S0 参数集中化与前置准备      → 产出：参数头文件 + 编译期断言
S1 观测器基础设施（影子）    → 产出：能算出角度，但不参与控制
S2 影子模式量化误差          → 产出：误差 < N° 的证据
S3 参数整定                  → 产出：最优补偿参数
S4 开环起动                  → 产出：起转成功率 10/10
S5 闭环切换                  → 产出：切换成功 + 闭环精度
S6 保护适配                  → 产出：异常场景全部有保护
S7 移植清单                  → 产出：换硬件可复现
```

**注意 S1/S2 的拆分**：先"能算"，再"算得准"。
把"实现"和"验证"拆成两个阶段，可以在实现有误时立刻发现，
而不是等到闭环失败时再回头猜。

## 6. 遇到的常见推进错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 边写边想需求 | 反复返工 | 先补 G1 |
| 跳过影子模式直接闭环 | 出问题无法区分"算法错"还是"接线错" | 按阶段走 |
| 一个提交里改五个东西 | 出问题无法归因 | 一次一改 |
| 用"看起来可以"代替数据 | 后续所有结论都不可信 | 上仪表 |
| 文档等"做完再补" | 补的时候已经忘了为什么 | 边做边记 |
| 保护误触发就放宽阈值 | 掩盖真问题，量产爆发 | 查清误触发的物理原因 |

## 7. 新工程启动模板

```markdown
## 项目：<名称>

### A. 需求（可验证）
| # | 需求 | 验收标准（可量化） | 优先级 |
|---|---|---|---|

### B. 约束
- 主控：<型号>，<主频>，<Flash/RAM>
- 外设：<列出使用的外设与引脚>
- 采样/控制频率：<数值>
- 物理量程：<电压/电流/温度…>

### C. 阶段计划
| 阶段 | 目标（可验证的能力） | 验收标准 | 依赖 |
|---|---|---|---|
| S0 | | | |

### D. 不做的事
- <明确排除的内容>

### E. 风险
| 风险 | 影响 | 对策 |
|---|---|---|
```

填写上述模板 = 完成 A 阶段，可进入 B。
