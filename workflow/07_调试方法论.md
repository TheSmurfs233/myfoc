# 07 调试方法论

> 本章是整个流程中最"贵"的部分——它来自 8 个真实 bug 的代价。
>
> 核心命题：**判断"系统是否正常"的判据本身，是最容易写错的东西。**

---

## 1. 第一原则：判据必须是物理不变量

### 1.1 什么是"物理不变量"

在工况变化时**保持不变**的量，才适合作为判据。

| 场景 | ❌ 会漂移的量 | ✅ 不变量 |
|---|---|---|
| 判断观测器是否锁住 | `eq`（投影分量，随角度差塌陷） | `\|e\| = √(eα²+eβ²)`（矢量幅值） |
| 判断电机是否在转 | 瞬时速度（抖动时穿越零点） | 低通后的速度 |
| 判断电流环是否正常 | 单个采样点 | 一段时间内的均值与纹波 |

### 1.2 案例：`eq` 为什么不能用

反电动势在估计坐标系上的投影：

```
ed = |e| · sin(θ̂ − θe)
eq = |e| · cos(θ̂ − θe)
```

当角度误差接近 90° 时，**eq ≈ 0，但 |e| 完全正常**。

用 `eq > 阈值` 当"反电动势足够大"的判据，等价于
"只有当角度误差恰好很小时才成立" —— 于是系统表现成**时好时坏**。

实测数据（同一命令，两次结果不同）：

| 尝试 | `eq/期望` | 结果 |
|---|---|---|
| 1 | 0.90 | 切换成功 |
| 2 | 0.12 | 卡住 |
| 3 | 0.03 | 卡住 |
| 4 | 0.04 | 卡住 |

**改用 `|e|/期望` 后：0.89~0.93，稳定通过。**

### 1.3 如何检验判据是否是不变量

问自己："如果系统的**其他**部分都不理想，这个量会变吗？"

- `eq` 会（随角度差变）→ 不是不变量
- `|e|` 不会 → 是不变量

## 2. 第二原则：不要用被验证的对象验证它自己

### 2.1 案例：切换判据的"自证"

```c
/* ❌ 用观测器自己的转速算期望值 */
expected = |omega_e| * psi;        /* omega_e 来自观测器 */
if (|e| > 0.5 * expected)  { 切换 }  /* 又用观测器算出的 |e| 判断 */
```

问题：观测器的 `omega_e` 一旦漂高（强制拖动阶段很常见），
期望值同步变大，**判据永远不成立** → 永远卡在等待状态。

```c
/* ✅ 用外部已知量算期望值 */
expected = drag_rpm * 2π/60 * pp * psi;   /* drag_rpm 是指令值，已知 */
if (|e| > 0.5 * expected) { 切换 }
```

### 2.2 通用形式

| 反模式 | 正确做法 |
|---|---|
| 用 A 的输出判断 A 是否正确 | 用**独立的** B 做基准（编码器、指令值、物理约束） |
| 用估算值判断估算是否收敛 | 用**可观测量**（电流、电压、时间） |
| 用模型的预测判断模型是否准 | 用**实测**做对照 |

### 2.3 没有独立基准时怎么办

如果确实没有第二个传感器（例如无编码器场合），则：
- 改用**物理约束**（如"转动必然产生反电动势"、"静止必然无电流"）
- 并明确记录"此处缺少交叉校验，误判无法被第二来源发现"

## 3. 第三原则：模式切换必须有硬优先级

### 3.1 案例：I/f 在切换后"复活"

系统结构：

```
速度环（先算） → 写 iq_ref
I/f 模块（后算） → 也写 iq_ref   ← 后者赢
```

切换完成后虽然调用了 `if_stop()`（`run = 0`），但：

```c
void if_set_target(v, f) {
    v->f_target = f;
    v->run      = 1;      /* ⚠️ 副作用：任何后续调用都会让已停止的模块"复活" */
}
```

于是任何一次"改目标"都会让 I/f 悄悄恢复，**并且继续覆盖速度环的输出**，
电机被钉在 I/f 的频率上动不了。

### 3.2 正确做法

```c
/* ① 去掉副作用 */
void if_set_target(v, f) { v->f_target = f; /* 不碰 run */ }

/* ② 在调度处加硬优先级（兜底） */
if ((if_run != 0) && (sensorless == 0)) {   /* 无感模式下 I/f 永不参与 */
    if_step();
}
```

**原则**：
- 状态切换不能只靠"停止标志"，必须有**结构性保证**
- 任何"setter"都不应该有"启动"这种副作用
- 后执行的模块必须显式检查"我是否有权执行"

## 4. 第四原则：先测量，再修改

### 4.1 反模式

```
现象：转速上不去
猜测 1：PI 饱和 → 改 PI → 无效
猜测 2：观测器带宽不够 → 改带宽 → 无效
猜测 3：电压不够 → 改限幅 → 无效
（三天过去）
```

### 4.2 正确流程

```
步骤 1：加仪表，把内部量打出来
        （调制比 m、iq、iq_ref、|e|、观测器转速、模式标志）
步骤 2：在**失败的那一刻**抓数据
步骤 3：让数据排除假设
步骤 4：只改被数据支持的那一处
```

### 4.3 案例：一次"仪表定生死"

现象：`sfoc go 1400` 有时卡在 600 rpm。

加诊断行后一次抓取：

```
sfoc: done, sensorless 1
 diag: if run 1 phase 1 f 70.00 Hz, ho cnt 400, |e|/exp 0.90
foc : ref 0.00/0.60, iq 0.14, vq 5.57, m 0.95
spd : ref 1400, meas 600
```

**一条信息就定位了**：
- `f 70.00 Hz` × 60/7 = **600 rpm** ← 正是卡住的值
- `iq_ref = 0.60` ← 正是 I/f 的拖动电流
- `if run 1` ← I/f 一直在跑

→ 结论：I/f 没退出，并且覆盖了速度环的电流参考。
（如果没打这几个量，只能继续猜。）

### 4.4 仪表设计要点

| 要点 | 说明 |
|---|---|
| 打印**内部状态**，不只打印输出 | 模式标志、计数器、饱和标志比"结果"更有信息量 |
| 打印**比例/一致性**，不只打印绝对值 | 如 `\|e\|/期望` 比 `\|e\|` 更能说明问题 |
| 打印**多个相关量在一起** | 便于交叉判断（`m` + `iq` + 角度） |
| 输出格式要**可被脚本解析** | 便于自动抓取与回归 |

## 5. 第五原则：一次只改一个变量

### 5.1 为什么

一次改三个东西且结果变好，你无法知道是哪个起了作用——
下次遇到类似问题，你依然不知道该怎么办。

### 5.2 对照实验的设计

```
基线：不改变任何东西，测三次，确认现象可复现
实验 A：只改 X，测三次
实验 B：只改 Y，测三次
对比：A/B/基线 的差异
```

### 5.3 案例：区分"跨度问题"与"状态问题"

现象：`spd 1400`（从 400 起跳）失败。

实验设计：

| 实验 | 操作 | 结果 |
|---|---|---|
| 1 | 跨度 100/200/…/1000 逐一测试 | **全部成功** |
| 2 | 用 `sfoc go` 复现原路径 | **卡住** |
| 结论 | 与"跨度"无关，与"命令路径"有关 | 转去查状态机 |

**如果只做实验 1 就收工，会误判为"跨度太大"**，
然后去改斜坡速率——完全修错方向。

## 6. 症状 → 根因 对照表（本工程实战版）

建立并维护这样一张表，是最高效的知识沉淀方式。

| 症状 | 首先怀疑 | 验证方法 |
|---|---|---|
| 状态一直停在"等待条件" | 判据用了会漂移的量 | 打印判据的各个分量，看哪个不满足 |
| 状态突然回到"空闲" | 有保护/异常路径把它复位了 | 搜所有能改该状态的地方；抓日志 |
| 卡在某个**恒定值** | 该值可能是某个**限幅/默认值** | 搜代码里等于该值的常量 |
| 电流指令恒定不变 | 有更高优先级的模块在覆盖它 | 检查执行顺序 + 模式门控 |
| 调制比顶到 0.9 以上、电流却很小 | 角度错，电压没在产生力矩 | 打印角度误差、`\|e\|`、`iq` |
| 速度反馈乱跳但角度正常 | 速度通道（PLL/窗口）被坏数据污染 | 看 CRC/错误计数、更新间隔 |
| 传感器读数"冻结" | 数据被丢弃，显示的是旧值 | 看有效标志与错误计数 |
| 全 0 帧通过校验 | 缺省数据恰好满足校验（如 CRC(0)=0） | 显式检查"全 0"并加"断线"检测 |
| 某功能在 A 模式正常、B 模式异常 | 数据源选择/优先级问题 | 打印"当前用的是哪个源" |

## 7. 假设被推翻时，必须显式记录

### 7.1 为什么

被推翻的假设是**最值钱的知识**：它防止你再走一次。

### 7.2 记录格式

```markdown
### 已推翻的假设
| # | 假设 | 推翻依据 | 真正原因 |
|---|---|---|---|
| 1 | 速度环积分饱和导致电压饱和 | iq 仅 0.08 A，未饱和 | I/f 覆盖了电流参考 |
| 2 | 1400 rpm 超出电压能力 | m=0.66，电压充足 | 交接判据不成立 |
| 3 | 编码器整体损坏 | 有感模式正常 | 角度通好、速度通道坏 |
```

## 8. 调试的收尾

问题解决后，必须完成三件事，否则这次调试的价值会流失：

1. **写进开发日志**：现象、数据、推理、修法、验证
2. **写进框架文档的"坑"章节**：后来者能直接看到
3. **若有可自动化的判据，加进主机测试**：防止回归

```c
/* 例：把"eq 不能用作判据"固化成断言 */
CHECK(emag_invariant_to_angle_error());   /* |e| 不随角度误差变化 */
CHECK(handover_uses_drag_reference());    /* 交接判据不依赖观测器自身速度 */
```

---

## 9. 一句话总结

> **判据设计错误的代价，远大于算法错误的代价。**
> 算法错了会立刻发散，判据错了会时好时坏——而"时好时坏"最难查。
