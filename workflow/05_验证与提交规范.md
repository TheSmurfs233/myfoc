# 05 验证与提交规范

> **提交不是"我改完了"，而是"我证明它没坏"。**
> 每一次提交都必须携带证据，否则它只是把不确定性推给了未来的自己。

---

## 1. 三方验证门禁

任何提交前，三条必须全绿：

| # | 验证 | 命令（按工程替换） | 通过标准 |
|---|---|---|---|
| 1 | **固件构建** | Keil `UV4 -r project.uvprojx` | **0 Error, 0 Warning** |
| 2 | **主机测试** | `bash test/host/build.sh` | `failed: 0` |
| 3 | **文档检查** | `python test/doc_check.py` | `PASS` |

### 为什么警告也要清零

- 警告是"编译器已经发现的可疑之处"，其中相当一部分是真 bug（隐式声明、未使用变量掩盖了拼写错误）
- 一旦允许警告存在，新警告就会被淹没在旧警告里
- 清零成本很低（通常一次到两次提交即可），收益是永久的

### 三方各自守什么

| 验证 | 守住的防线 |
|---|---|
| 构建 | 语法、类型、链接、资源占用（Flash/RAM 是否够） |
| 主机测试 | 算法正确性、边界、回归（防止"修好 A 改坏 B"） |
| 文档检查 | 文档与代码的一致性（版本号、命令数、通道数、表格结构） |

**三者互补，缺一都会漏**：构建通过但算法错、算法对但文档过期，都是常见失败模式。

## 2. 版本号规则

### 2.1 单调递增，只增不减

```c
#define FW_BUILD_ID  163u   /* 每次可烧录的改动 +1 */
```

- **每次要烧录的改动都必须 +1**（哪怕是改一行）
- 不烧录的改动（纯文档、纯测试）不 +1
- 一旦发布，不覆盖旧版本号（回退时用新的版本号 + 回退说明）

### 2.2 版本号是"证据锚点"

```
开发日志：实测 5/5，固件 #163
进度表：  S5 完成，证据 #163
波形通道表：适用于 #161 之后
```

有了它，才能回答："这个结论是哪个固件测出来的？"

### 2.3 启动时打印

```
[log] build = Nov  1 2026 12;00;00 #163
```

**没有版本号的固件等于无法追溯的实验**。

## 3. 提交信息规范

### 3.1 结构

```
<一句话标题（做了什么，≤ 50 字）>

<问题/背景：现象 + 触发条件>

<根因：为什么会出现>

<修法：怎么改的，关键决策及理由>

<验证：构建 / 测试 / 实测数据>
```

### 3.2 正面示例

```
交接判据的期望值改用拖动转速，而不是观测器自身转速（#163）

现象(13:21): 同样的 sfoc go 600 两次行为不同 —— 一次 1.8 秒交接成功,
另一次一直停在 watching, I/f 拖在 600 rpm 不动

根因: 判据是 |e| > 0.5*(|omega_e|*psi), 用观测器【自己的】转速去验证它自己
  强制拖动阶段观测器的 omega 一旦漂高, 期望值跟着变大, 判据永远不成立

修正: 期望值改用【拖动指令转速】rpm_if (已知量, 不受观测器影响)
  w_exp  = rpm_if * 2pi/60 * pp
  eq_ex2 = w_exp * psi
  sfoc 的 diag |e|/exp 也用同一参照, 便于判读

验证: Keil 0E/0W Code=61974; 主机 538/0 PASS
```

### 3.3 反例

| ❌ | 问题 |
|---|---|
| `update` | 什么都没说 |
| `fix bug` | 哪个 bug |
| `修改了一些问题` | 无法检索、无法回滚判断 |
| `优化` | 优化了什么指标？前后对比？ |

### 3.4 为什么"根因"必须写

三个月后你会问"为什么这段代码这么写"。
如果提交信息里有根因，答案就在 `git log` 里；
如果没有，你只能重新调试一遍——而且很可能再次踩同一个坑。

## 4. 一次提交改一件事

| 做法 | 结果 |
|---|---|
| 一个提交 = 一个逻辑改动 | 出问题能精确定位、能单独回滚 |
| 一个提交 = 五个改动 | 无法归因；回滚会波及其他 |

**例外**：同一个改动的"代码 + 对应文档 + 测试断言"应当放在同一个提交里
（否则历史里会出现"文档描述了不存在的行为"的中间状态）。

## 5. 分支与推送

### 5.1 分支模型（小团队 / 个人）

```
master          稳定线，只接受"已验证"的合并，不直接开发
feature/<主题>  所有开发在这条线上
```

规则：
- `master` 上的每个提交都应该是"可交付"的
- 大改动（多阶段）在 feature 分支走完，何时合并由负责人决定
- **决定不合并时也要写下来**（在 `01_项目进度` 或 `00` 里记录决策与理由）

### 5.2 推送策略

- 每个"阶段完成"或"重要修复"后推送
- 推送失败（网络/TLS）时**重试**，不要跳过（本地提交不算交付）
- 推送前确认 `git status` 干净（无未提交改动）

### 5.3 里程碑标签

```bash
git tag -a v0.5-S8 -m "S8 完成：速度环+PLL 观测器，ripple 0.06A/11rpm"
```

标签信息里写**可验证的成果**，不要只写版本号。

## 6. 提交前检查清单

```markdown
- [ ] 构建 0 Error 0 Warning
- [ ] 主机测试 failed: 0
- [ ] 文档检查 PASS
- [ ] 版本号已递增（若需烧录）
- [ ] 相关文档已同步（进度表/框架文档/参数表/命令手册）
- [ ] 提交信息含"问题/根因/修法/验证"
- [ ] 一次提交只包含一个逻辑改动
- [ ] 已推送
```

---

## 7. 回滚规范

出问题时：

1. **先记录现象**（回滚会破坏现场）
2. 用 `git revert`（而不是 `reset --hard`）保留历史
3. 回滚提交里写明"回滚什么、为什么、后续如何处理"
4. 版本号继续递增（回滚也是一次烧录改动）
5. 在 `90_已知问题` 里登记该问题（避免再次尝试同样的方案）

## 8. 自动化（可选进阶）

把三方验证写成一个脚本，一条命令跑完：

```bash
#!/usr/bin/env bash
# verify.sh
set -e
echo "== 1/3 build =="
UV4 -r MDK-ARM/project.uvprojx -j0 -o build.log
grep -E "0 Error\(s\)" build.log
echo "== 2/3 host tests =="
bash test/host/build.sh | grep -E "failed: 0"
echo "== 3/3 doc check =="
python test/doc_check.py
echo "ALL GREEN"
```

**规则：`verify.sh` 不绿就不许提交。**

### 8.1 调用方式必须写死

验证脚本最大的隐患是"跑在错误的环境里"：
同一个 `build.sh`，用 WSL 的 `bash` 跑和用工具链自带的 `bash` 跑，
可能一个报"找不到文件"、一个报"缺 `-lm`"——而真正的错误被掩盖。

要求：

| 要求 | 做法 |
|---|---|
| 显式指定 shell | 文档里写完整可执行的命令，不止写 `bash xxx.sh` |
| 脚本自证环境 | 开头打印 `gcc --version`、`BASH_VERSION`、关键路径 |
| 失败即停止 | `set -e`；`gcc ... \|\| exit 1` |
| 输出可判定 | 只输出关键行（`0 Error`、`failed: 0`、`PASS`） |

```bash
# 例：把"用哪套工具链"固化成一行
D:\Xilinx\Vitis_HLS\2022.2\tps\win64\msys64\usr\bin\bash.exe -lc \
  "cd /d/<项目> && bash test/host/build.sh"
```
