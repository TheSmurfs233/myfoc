# 03 阶段推进与验收

> 阶段划分决定项目能不能"稳步推进"。
> 划分得好：每个阶段失败都是局部的、可归因的；
> 划分得差：一个失败就要推翻重来。

---

## 1. 好阶段的四个特征

| 特征 | 检验方法 |
|---|---|
| **产出一种可独立验证的能力** | 能用一句话说清"它能干什么" |
| **验收标准可量化** | 有数值阈值或明确的通过/失败判据 |
| **失败是局部的** | 这个阶段失败，之前的成果依然有效 |
| **1~5 天可完成** | 超过就再拆一层 |

---

## 2. 阶段拆分方法

### 2.1 按"能力链"拆，不按"代码模块"拆

❌ 错误：按代码模块拆（"先写驱动层，再写算法层"）
—— 无法验证，因为每层单独都没法证明"对了"

✅ 正确：按能力拆（"能读角度" → "角度准" → "能用角度做电流环"）
—— 每步都有可观测的产出

### 2.2 "能做" 与 "做得对" 必须分开

这是本流程最关键的拆分技巧：

| 阶段类型 | 产出 | 验证方式 |
|---|---|---|
| **能力阶段** | 功能"能跑起来" | 有没有输出、有没有动作 |
| **精度阶段** | 功能"跑得准" | 误差指标、重复性、边界表现 |

例：

```
S1 观测器能算出角度（能跑）        → 验证：角度在 0~360° 内变化
S2 观测器算得准（准不准）          → 验证：与编码器对比误差 < N°
```

**好处**：如果 S2 不达标，你知道问题在"算法精度"而不是"接口没通"。

### 2.3 影子模式（Shadow Mode）原则

任何**要接管控制的新算法**，先以"只读/只算"的方式并行运行，
与现有可信来源对比，达标后再接入控制回环。

```
阶段 1：新算法只计算、不使用（影）
阶段 2：对比新旧输出，量化误差（验）
阶段 3：切换控制权（切）
阶段 4：保留切换开关，可随时回退（留）
```

**收益**：新算法永远不会"直接把系统搞崩"，且切换有据可依。

## 3. 阶段文档（开工前必须写）

每个阶段开工前，写一份 `templates/t_阶段方案.md`，包含五节：

```markdown
## S<n> <阶段名>

### 1. 目标（可验证）
- 能 <做什么>，验收标准：<可量化>

### 2. 非目标（本阶段不做）
- <明确排除>

### 3. 技术路线
<怎么做；若有备选，写明为什么选这条>

### 4. 验证方法
<怎么证明它成了；用什么命令/脚本/仪器>

### 5. 风险与对策
| 风险 | 影响 | 对策 |
```

> **不写方案的阶段不允许开工**。
> 方案的价值不在于"正确"，而在于逼你想清楚"怎么证明它成了"。

---

## 4. 验收标准怎么写

### 4.1 四种合格的验收标准

| 形式 | 示例 |
|---|---|
| **成功率** | 连续起转 ≥ 9/10 成功 |
| **精度** | 稳态误差 < 1%；角度误差 < 3° |
| **阈值** | 超调 < 10%；建立时间 < 50 ms |
| **行为** | 断电后 200 ms 内桥臂关断，无过冲 |

### 4.2 不合格的写法

| ❌ 写法 | 问题 |
|---|---|
| "运行正常" | 无法判定 |
| "性能良好" | 无阈值 |
| "满足要求" | 要求本身没定义 |
| "基本可用" | 不可验证 |

### 4.3 验收标准要写"如何测"

```markdown
| 项 | 标准 | 测法 |
|---|---|---|
| 起转成功率 | ≥ 9/10 | `sfoc go 400` 连续 10 次，记录 `sfoc` 的 `state=done` |
| 稳态误差 | < 1% | 每个目标转速保持 3 s 后读 `spd` 的 `meas` |
```

## 5. 验收执行规范

### 5.1 用脚本，不用手

每个阶段配一个验收脚本（`test/accept/sN_accept.py`），要求：

- 参数化（目标转速、次数、容差）
- 输出**结构化结果**（PASS/FAIL + 实测值）
- 可重复运行（不受上一次状态影响：开始时先 `stop` 复位）
- 失败时打印**当时的完整状态**（不只是"失败"）

```python
# 结构示意
def accept_startup(s, n=10, rpm=400):
    ok = 0
    for i in range(n):
        reset(s)                       # 复位到已知状态
        s.write(b'sfoc go %d\r\n' % rpm)
        if wait_state(s, 'done', timeout=5):   # 等到期望状态
            ok += 1
    return ok >= n * 0.9, f'{ok}/{n}'
```

### 5.2 记录"失败那一次"的数据

失败是随机的，所以**必须在失败发生的那一刻抓状态**，
而不是事后复盘（事后状态已经变了）。

做法：脚本在判断失败时，立刻 dump 所有相关寄存器/内部变量/日志。

### 5.3 验收通过后必做三件事

1. 数据写入 `00_开发日志`（含日期、固件版本、测试条件）
2. `01_项目进度` 更新状态 + 证据
3. 相关框架文档补充"新发现的坑"

## 6. 阶段的"回退"规则

情况：阶段 N 进行中发现阶段 N-2 有缺陷。

**正确做法**：
1. 在 `00` 记录发现的问题与证据
2. 在 `01` 把阶段 N-2 改回 `🟡 进行中`，写明原因
3. 修好 N-2 并重新验收
4. 再回到 N

**错误做法**：在阶段 N 里"顺手绕过"——这会让 N 的结论建立在错误前提上。

---

## 7. 一个完整阶段的生命周期（示例）

```markdown
## S5 闭环切换

**方案**（提前写）
- 目标：交接成功率 ≥ 9/10，交接时间 < 2 s，切换无转速跌落
- 非目标：不处理起转失败自动重试
- 路线：判据用 |e| 幅值 + 拖动转速一致性；角度渐变 100 ms
- 验证：脚本连跑 10 次，记录 state/时间/跌落

**实施**
- 加 `app_ho_*` 状态机；固件 #145
- 判据初版用 `pll.locked`（后来证明是错的，见下）

**验收（第一次）**
| 项 | 标准 | 实测 | 结论 |
|---|---|---|---|
| 成功率 | ≥ 9/10 | 7/10 | ❌ |
| 交接时间 | < 2 s | 1.8 s | ✅ |

**归因（关键步骤）**
- 失败样本全都是 `state=watching` 卡住
- 打印 `diag` 发现 `ho cnt` 一直为 0，说明判据没成立
- 查代码：判据里用了 `pll.locked`，而它是瞬时标志，随纹波翻转
- **结论：判据用错量**（与算法无关）

**修复 + 二次验收**
- 判据改为 `|e|` 幅值 + 拖动转速一致性 → 固件 #155/#163
- 实测 5/5，1.8 s ✅

**沉淀**
- `07_调试方法论` 新增："判据只能用物理不变量"
- `00` 记录两次验收数据与推翻过程
- `01` 标记 S5 ✅，证据：#163，5/5
```

**注意**：这次"失败 → 归因 → 修复"的过程本身，
比"一次通过"更有价值——它产出了可复用的方法论。
