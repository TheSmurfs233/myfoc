# 06 硬件与安全约定

> 软件可以回滚，硬件不能。烧毁的 MOS、飞出去的转子、丢失的标定数据，都不会自己回来。
>
> 本章的规则不是"谨慎一点"，而是**明确的授权边界与红线**。

---

## 1. 授权模型

### 1.1 必须先请示的动作

| 动作 | 为什么 |
|---|---|
| **烧录固件** | 板上状态改变，可能带载、可能失控 |
| **打开串口** | 独占端口，会与用户的终端冲突；且发命令会驱动电机 |
| 上电 / 断电 | 带电插拔风险；可能丢失未保存的标定 |
| 拆接线缆 | 编码器/传感器接线错位会导致错误控制 |
| 修改保护阈值 | 直接关系安全 |
| 让电机带载运行 | 机械风险 |

### 1.2 可以直接做的动作

- 读代码、读文档、写文档
- 修改源码（不烧录）
- 运行主机测试、文档检查
- 构建（不下载到板子）

### 1.3 冲突处理

串口被占用（`PermissionError(13)`）时：
- **不要**尝试强制关闭用户的终端
- 告知用户"端口被占用，请关闭终端后我再来"
- 或者让用户自己发命令、把输出贴给你

## 2. 安全红线（永远不做）

| # | 红线 | 原因 |
|---|---|---|
| 1 | **不为让测试通过而放宽保护阈值** | 掩盖真问题，量产时爆发 |
| 2 | **故意制造过流/过压去"测试"保护** | 可能烧毁硬件；保护测试用**慢速逼近**或软件注入 |
| 3 | **在运行中改控制参数做"实验"** | 可能进入不稳定区，损坏机械 |
| 4 | **跳过限幅/饱和处理** | 实际系统 90% 的故障源于饱和 |
| 5 | **用固定角度强行驱动未知转子位置** | 大电流 + 错误角度 = 过热或退磁 |
| 6 | **在未确认电流方向的情况下开环给电流** | 可能产生与预期相反的力矩 |

## 3. 保护测试的正确方法

### 3.1 不要"制造危险"去验证保护

| 保护 | ❌ 错误做法 | ✅ 正确做法 |
|---|---|---|
| 过流 | 短路一相 | 软件注入：把阈值临时调到正常工作点以下（在方案允许范围内），或用假数据走主机测试 |
| 过压 | 提高母线电压到危险值 | 软件注入假 VBUS 值（主机测试）或确认阈值后接受一次实测 |
| 堵转 | 用手硬顶（有机械风险） | 手动堵转需缓慢加阻，且**先确认保护判据与时限**；或降低目标转速让其自然堵转 |
| 失步 | 强行给不匹配的角度 | 制造"反电动势消失"的条件（断电或用假数据） |

### 3.2 手动堵转的标准流程

```
1. 先确认堵转保护的判据、阈值、时限（读代码，不看文档）
2. 低速运行（如 400 rpm），确认 iq 远小于限幅
3. 缓慢加阻（不是猛按），观察 iq 上升、转速下降
4. 记录跳闸时间与跳闸时的值
5. 跳闸后确认：桥臂关断、故障码正确、恢复流程可用
```

### 3.3 保护验证必须记录的数据

| 项 | 例 |
|---|---|
| 触发条件 | 堵转，iq=1.20 A（限幅），转速 < 30 rpm |
| 触发时间 | 从施加阻力到跳闸 ≈ 500 ms |
| 动作结果 | PWM OFF，duty = 0.5/0.5/0.5，state=FAULT |
| 恢复方式 | `stop` → `mode 2` → `start` |

## 4. 硬件异常时的排查顺序

当"软件看起来对但硬件行为不对"时，**先怀疑硬件，再怀疑代码**——但要**用数据确认**，不要直接下结论。

### 4.1 标准排查顺序

```
1. 供电（电压、电流、纹波）
2. 连接（排线、焊点、连接器）
3. 传感器（输出是否合理、有无异常标志）
4. 功率级（MOS、驱动、死区）
5. 最后才是控制代码
```

### 4.2 案例：编码器"降级"的识别

现象：无感运行时行为时好时坏，速度读数乱跳。

错误结论："编码器坏了，有感模式也该不work" —— 但实际上有感模式正常。

正确分析（用数据）：

| 观测 | 数据 | 推理 |
|---|---|---|
| CRC 错误率 | 80% | 链路在丢数据 |
| 但仍有 20% 好帧 | 4 kHz 有效帧 | **角度仍然可用**（FOC 只需角度） |
| 速度乱跳 | PLL 只在好帧更新 | **速度通道被污染** |
| `mg` 字段异常 | 磁场状态位变化 | 磁铁/传感器间距可能被扰动 |

**结论**：角度通道正常、速度通道损坏 —— 所以有感能跑、无感对比失效。

**方法论**：不要用"整体好坏"判断，要**分通道判断**（每个数据路径单独看）。

## 5. 上电/掉电与故障恢复

### 5.1 上电顺序要求

必须写进文档并在代码里体现：

1. 初始化时钟、GPIO（**先把功率级置为安全态**：所有开关管关断）
2. 读标定数据（校验失败要有安全默认值，不能带病运行）
3. 校准电流零漂（此时功率级必须关断）
4. 使能外设
5. 进入待机状态（等命令）

### 5.2 故障恢复流程必须固定

```
FAULT → 用户执行 stop（清除故障） → 重新 start → 重新进入工作流程
```

要求：
- 故障状态下**拒绝一切会驱动功率级的命令**，并明确报错
- 故障码与故障值要保留（供事后分析），只在 `stop` 时清除
- 故障类型要能区分（过流/过压/堵转/传感器/…）

### 5.3 标定数据的保护

- 标定值存 Flash 时带 **magic + CRC**
- 读到损坏数据 → **使用安全默认值并告警**，不要用垃圾值运行
- 提供"恢复出厂值"的路径
- 关键标定（如角度零位）要有**备份文档**（记录数值与恢复命令）

## 6. 现场调试的实用约定

| 约定 | 原因 |
|---|---|
| 调试前先记录当前固件版本与标定值 | 出问题可回到已知状态 |
| 每次只改了"一个东西"再烧 | 否则无法归因 |
| 烧录后先跑"最小动作"验证（如 `stat`） | 确认固件真的在跑 |
| 带载测试前先空载验证 | 排除控制问题后再加载 |
| 电机运行时人不要接触旋转部件 | 基本安全 |
| 串口日志要保存下来 | 现象会消失，日志不会 |

## 7. 硬件变更的文档要求

任何硬件改动（换电机、换编码器、改电路），必须更新：

1. `19_硬件资源与引脚映射.md`（如有引脚变化）
2. `31_参数表.md`（电气参数）
3. `90_已知问题`（旧问题是否还适用）
4. `00_开发日志`（何时、改了什么、为什么）

并在 `01_项目进度` 重启相关阶段的验证（**不要假设旧结论仍成立**）。
