## 1. ① 速度 PLL 失锁后自由振荡 🔴

### 现象（真机实测）

`stop` 之后桥臂已关断、转子**机械角完全不动**（连续两次读数都是 214.4°），
但速度读数停在 **2000 rpm**（正好是 `w_max` 限幅值）长达约 6 秒：

| 时间 | 机械位置 | 速度读数 |
|---|---|---|
| 5.67 s | 214.4°（已停） | 1999.6 rpm |
| 7.29 s | 214.4° | 1937.8 rpm |
| 9.74 s | 214.4° | 1877.9 rpm |

### 根因

二阶（type-2）PLL 的固有缺陷：

```
θ̂ 以 ω̂ 继续累加 → 与静止的真实角度的误差变成锯齿波
→ 误差在一周期内正负抵消 → 积分器输入平均为 0 → ω̂ 不衰减
```

当 `|ω_true − ω̂|` 超出捕获范围（约 ±20 Hz 电频率 = ±170 rpm）时，
环路**无法把速度拉回来**，会一直自由旋转。

master 的 `mid_enc.c` 在帧间隔 ≥2 ms 时会走"gap"分支，只 reset 角度、
**保留 omega 且不更新 `spd_rpm`**，所以读数既不衰减也不刷新。

### 危害

| 场景 | 后果 |
|---|---|
| **运行中机械堵转** | 速度读数仍是 1500~2000 rpm → 堵转保护（`\|spd\| < 30`）**永不触发** |
| RUN 状态下静止 | 会**误报超速**（读数撞限幅） |
| stop / 故障后 | 速度显示错误，误导判断 |

### 为什么 S8 验收没发现

S8 的验收都是让电机**平滑减速**（`spd 0` 有斜坡），PLL 全程跟得上；
没有"高速时突然断桥臂"这个用例。

### 修复（#136）

```c
void mid_enc_pll_clear(void)   /* 清 omega + 角度对齐 + 速度归零 + 清窗口 */
```

调用点只有两个，**只在状态切换时执行一次**：

| 位置 | 说明 |
|---|---|
| `app_stop()` | stop / 模式切换 |
| `app_fault_raise()` | 故障后桥臂关断 |

**为什么不用"运行中的静止检测"**：#135 试过（`|机械角变化| < 0.2°` 持续 50 ms
且 `|PLL| > 300 rpm`），结果与上面那个 gap 路径互相踩 —— IDLE 下帧间隔正好
约 2 ms，每次更新都走 gap 分支，`spd_rpm` 冻结在旧值，检测反复触发，
速度环读到 0 后把电流拉满，**实测直接过流跳闸**。已撤回。

### 仍未解决的部分

**运行中**机械堵转（不发生状态切换）仍可能让读数偏高。
此时可靠的是：

- 电流限流 `FOC_I_MAX_A = 1.20 A`
- 过流跳闸 `FOC_I_TRIP_A = 1.28 A`（5 帧）

已在 `docs/17` 记为该保护机制的已知局限。

### 同步到 master 需要

1. `mid_enc.c/.h`：新增 `mid_enc_pll_clear()`（+ 顺带 ②）
2. `app_main.c`：`app_stop()`、`app_fault_raise()` 各加一行
3. `app_cmd.c`：`enc` 显示 `pll clears`

## 2. ② 窗口估计器大间隔后留下旧值 🟡

### 现象

排查 ① 时用波形通道抓数据，发现转子静止时：

```
ch17 win_rpm : 1809.50（430 帧完全不变 ← 冻结）
ch18 pll_rpm : 907.26（在变）
ch7  mech_deg: 160.94（确实静止）
```

### 根因

master 的 gap 分支只清累加器，不清输出：

```c
} else if (dt > (2u * SYS_CORE_CLK_HZ / 1000u)) {
    s_acc_mech = 0.0f;
    s_acc_elec = 0.0f;
    s_acc_cyc  = 0u;
    /* ← s_win_rpm 保留旧值 */
}
```

### 危害

任何读 `s_win_rpm` / `mid_enc_win_rpm()` 的地方（波形、`enc`、对比测试）
都会看到一个**冻结的假速度**，误导诊断。

### 修复（#136）

gap 分支补一行 `s_win_rpm = 0.0f;`。

## 3. ③ `clr` 不清编码器错误计数 🟡

### 现象

```
clr          →  "OK counters cleared"
enc          →  err = 4247/643871 crc    ← 还是 4247
```

### 根因

```c
void app_counters_clear(void) {
    s_st.wave_frames = 0u;
    s_st.wave_drop   = 0u;
    s_st.rx_drop     = 0u;
    /* 没有编码器部分 */
}
```

### 危害

无法测量"某段时间内的 CRC 错误率"（只能看累计值）。
验收时需要这个指标来判断 EMI 是否变差。

### 修复（#129）

- `mid_enc.c/.h`：新增 `mid_enc_clear_errs()`（清 crc/ovr/late/io，`frames` 继续累加，便于算比率）
- `app_counters_clear()` 调用它

## 4. ④ `app_align_start()` 返回值 3 不可达 🟡

### 根因

```c
if (s_st.state != APP_ST_RUN) { return 2u; }   /* 先查状态 */
if (s_align.active != 0u)     { return 3u; }   /* 永远走不到 */
```

开始对齐本身就会把 `s_st.state` 改成 `APP_ST_ALIGN`，所以第二次调用总是返回
2（"先 start"）而不是 3（"已在对齐"）。

### 危害

只是错误提示文字不准，功能没问题。

### 修复（#129）

把 `active` 判断提到状态判断之前（两个入口都改），
并加主机测试覆盖 `0/2/3` 三种返回值。

## 5. ⑤ 死代码：`MOTOR_RS_OHM` / `MOTOR_LS_H` ⚪

```c
/* master 的 board_cfg.h 末尾 */
#define MOTOR_POLE_PAIRS        7u      /* [TBD] pole pairs */
#define MOTOR_RS_OHM            0.5f    /* [TBD] phase resistance */
#define MOTOR_LS_H              0.001f  /* [TBD] phase inductance */
```

**全仓库 0 处引用**（已用 `git grep` 确认），且数值是错的（0.5 Ω / 1 mH，
实际 2.3 Ω / 0.5 mH）。留着会误导，而且与新增的 `motor_cfg.h` 命名冲突。

**修复**（S10.0a，`f31640c`）：删除，参数统一到 `User/Cfg/motor_cfg.h`。

## 6. 这些问题是怎么被发现的

| # | 触发场景 | 发现方式 |
|---|---|---|
| ① | 验证 #133 标定后做收尾检查 | 注意到"状态 IDLE 但速度 2000 rpm"，用波形通道确认 |
| ② | 排查 ① | 波形 ch17/ch18 对比，发现 ch17 完全不变 |
| ③ | #128 真机验证 | `clr` 后 CRC 计数没变，测不出错误率 |
| ④ | 加 `align ol` 时写主机测试 | 断言 `== 3u` 失败 |
| ⑤ | 新建 `motor_cfg.h` | 编译报重复定义 |

**共性**：都是"为了验证新功能而写的检查"顺带发现的。
这说明**可观测性（波形通道、命令输出、主机断言）本身就在帮找 bug**。
