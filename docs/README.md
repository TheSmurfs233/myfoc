## 文档统一模板

每个框架文档固定 7 节：

```
1. 职责边界    —— 这个模块做什么，不做什么
2. 接口        —— 对外 API / 数据结构
3. 关键参数    —— 相关宏、寄存器值、计算公式
4. 时序/数据流 —— 什么时候被调用，数据从哪来到哪去
5. 依赖        —— 依赖谁、被谁依赖
6. 验证方法    —— 怎么在台架上证明它是对的
7. 已知限制与 TBD —— 没解决的坑
```

## 编译与验证（命令行，不依赖点鼠标）

本机 Keil 在 `D://installfile//Keil_v5`，可以直接命令行全量编译，**每次改完代码都应跑一次**：

```bash
"D:/installfile/Keil_v5/UV4/UV4.exe" -b \
  "D:/Embedded/STM32/dsh_foc/MDK-ARM/myfoc.uvprojx" -j0 -o \
  "D:/Embedded/STM32/dsh_foc/MDK-ARM/build.log"
```

- 返回码 `0` = 成功；`1` = 有警告；`2` = 有错误
- 结果看 `MDK-ARM/build.log`，产物在 `MDK-ARM/myfoc/myfoc.axf` / `.hex`
- **每次换一个日志文件名**（`build2.log`、`b15.log`…）：Keil GUI 开着时同名 log 可能不被覆盖，
  会读到上一次的结果。**以返回码为准，别只看 log 内容。**
- 基线（2026-10-31，S10 / #154）：`Code=53778 RO=2398 RW=436 ZI=9868`，RAM 占用 9.2KB / 32KB

### 源码编码红线（踩过坑）

**所有 `.c/.h` 必须纯 ASCII**（注释和字符串都用英文）。

原因：Keil **ARMCC V5** 按 GBK 解析源码。UTF-8 中文的最后一个字节常是
`0xA9/0xAE/0xAF` 这类 GBK 前导字节，会把紧跟其后的 `"` 吞成双字节字符 →
报 `#8: missing closing quote`。中文**注释**多数情况下能过，中文**字符串**必崩。

- 中文说明一律写进 `docs/`（本目录）
- 串口输出用英文，还能避免各种串口助手/VOFA+ 的乱码
- 改完代码可用下面命令自检：`grep -rP "[\x80-\xff]" User/`

## 维护约定

- **每次代码改动，同一次提交内更新**：对应框架文档（若接口/参数变了）+ `00_开发日志.md`（新增一条）+ `01_项目进度.md`（状态变了才改）。
- 开发日志**倒序**（最新在最上方），只增不改。
- **动手之前先问**（用户 2026-10-25 明确要求）：
  - **烧录**（`UV4 -f` 或任何写 Flash 的操作）前必须先获得同意；
  - **打开/占用调试串口**（COM7 等）前也必须先获得同意 —— 串口是独占资源，
    用户可能在用 VOFA+ 或串口助手。
  - 一句话：改代码、编译、跑主机测试随时可以做；**碰硬件（烧录 / 开串口）先问一句**。
- 新增 `【TBD】` 必须同步登记到 `18_待确认清单.md`，解决后打勾并写明结论。
- **分支约定**：`master` 是稳定线（已验收、可烧录）；新功能在独立分支开发。
  **是否合回 `master` 由需求决定，不强制**：
  - 想保留两条线（如"有感版本"与"无感版本"并存）→ 分支长期独立存在；
  - 想让无感成为主线 → 验收通过后合回，或直接把 `master` 快进到该分支。
  - 当前的功能分支：`feature/sensorless-foc`（无感 FOC，见 `33_无感FOC评估.md`），
    目标是 300~1800 rpm 闭环 + I/f 启动。
- **每个阶段（S 级）收尾时跑一次** `python test/doc_check.py`：
  它检查乱码、表格截断、`help`/波形通道/版本号漂移，并列出"当前状态"类文档里
  仍残留 `TBD`/`待测`/`未开始` 的正文（自动跳过历史日志与 TBD 汇总表）。
  起因是 S8 收尾时发现 `01_项目进度.md` 的正文四节还停在 S3 状态。
- **参数"纯重构"不能只靠编译通过验证**：浮点常量写错时 Keil 依然 0 Error / 0 Warning，Code 字节数也可能完全不变。因此：
  1. 电机参数有**编译期范围断言**（`motor_cfg.h` 的 `MOTOR_CFG_ASSERT`，ARMCC5 无 `_Static_assert`，用负数组技巧）；
  2. 主机测试有**关键参数快照**（`cfg: motor parameter golden values`），任何越界都会在 `test/host` 阶段失败；
  3. 改参数后必须人工验算派生量（如 `J/Kt`）。
- 文档里出现的数字（ARR、死区、增益、阈值、缓冲大小、速率上限）必须与代码中的宏**一致**，
  改代码必须同改文档。
- **改完任何一个宏，必须全仓库 grep 旧值**（包括代码注释、文档表格、帮助文案），
  确认没有残留：

  ```bash
  grep -rn "<旧值>" docs/ User/ | grep -v 开发日志
  ```

  > 2026-10-25 踩过：`DBG_WAVE_RATE_MAX` 从 300 改到 500 后，`help` 文案改了，
  > 但 `docs/15` 命令表、`docs/01`/`docs/18` 的 S6 提醒、`app_main.c` 的注释
  > 都还写着 300Hz —— 被用户发现。

- **不要用 PowerShell 的 `Get-Content` / `WriteAllText` 改 UTF-8 文档**（2026-10-25 踩过）：
  Windows PowerShell 5.1 的 `Get-Content -Raw` 默认按 **GBK** 解码，再 `WriteAllText` 写成 UTF-8，
  中文会被二次编码成 `涓€閽?` 这类乱码，而且 GBK 解码失败的字节变成 `?` 后**不可逆**。
  - 改文档一律用编辑工具（或 Python 显式 `encoding='utf-8'`）；
  - `git restore` 是唯一的兜底恢复手段（本次丢了 `README.md`/`01`/`00` 三个文件的当日改动，靠重写补回）。
  - 自检：`python -c "print(open('docs/01_项目进度.md',encoding='utf-8').read().count(chr(0xFFFD)))"`
    输出必须为 0。
